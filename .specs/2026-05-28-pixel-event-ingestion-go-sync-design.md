# Pixel Event Ingestion — Go Sync External Event — Design Spec

**Date:** 2026-05-28
**Status:** Approved
**Bounded Context:** cross-context: `contracts` + `webhooks` (Go) + `sync` (Go) — consumed downstream by TS `tracking` + `sales` (already built)
**Kind:** feature
**Story Points:** 8 — additive contract enum value + regen, a new `sync.external_*` event family member (mapper + internal event + handler + canonical struct + channel-drain storage + Redis throttle + 24h backfill service + a cached sales-channel resolver) and a `type=PIXEL_EVENT` intake branch, all inside one service reusing the existing webhooks→sync pipeline; no migration (table exists), no new TS endpoint (resolver is a Go-direct read), and the output integration event already exists.

## Context

The pixel system was **contract-locked and the read-side built** in a prior pass — only the Go write path is missing. Concretely:

- **Contracts** (`packages/contracts/wire/`): `PixelEventType` (`wire/enums/pixel-event-type.tsp`, 8 values), the output integration event `PixelEventRecordedEvent` = `integration.shared.pixel_event.recorded` (`wire/events/pixel-event-recorded.tsp`), and `CartLinkedToOrderEvent` (`wire/events/cart-linked-to-order.tsp`, out of scope here). The `PixelEventRecordedEvent` docstring states the intended owner: *"Published by **go-worker** after a pixel event is ingested. TS Tracking projects the funnel; TS Sales subscribes to CHECKOUT_COMPLETED to link Cart→Order."*
- **DB** (`packages/contracts/db/schema/tracking.ts`): `tracking.pixel_events` already exists with the full shape — `unique(platform, external_event_id)` for dedupe, `visitor_key`, `utm` (jsonb), `cart_external_id`, `product_external_id`, `url`, `referrer`, `occurred_at`, `ingested_at`, indices for funnel (`event_type`, `occurred_at`) and cart-linking (`cart_external_id`) and visitor stitching (`visitor_key`). **There is no `retroactive` column.** `sales.carts` (`db/schema/sales.ts`) is the Go-owned Cart projection — out of scope.
- **TS read-side** (`packages/api/typescript/src/tracking/`): `GetPixelFunnel` (`usecases/GetPixelFunnel.ts` — counts + `uniqueSessions` + drop-off per canonical stage) and `GetPixelScriptSnippet` (`usecases/GetPixelScriptSnippet.ts` — emits the Shopify storefront bundle wired with `storeIntegrationId`). Both already shipped; Tracking owns no commands.

The Go side already ingests **signed provider webhooks** through a single unified pipeline that pixel will join:

- `webhooks/controllers/webhook.go` — `POST /webhooks?platform&event&integrationId&storeId`: decodes + validates (`event` ∈ `wire.SyncEventName`), verifies the per-platform HMAC, then saves a `WebhookReceivedEvent` (deduped by `IDFromSeed(... sha256(body))`) to the outbox and returns **202**.
- `webhooks/handlers/webhook_received_handler.go` — off the outbox (`core/services/outbox/outbox_dispatcher.go` → `InternalMediator`), resolves `mappers.Factory.Get(platform, event)` (`webhooks/mappers/factory.go`), maps the raw body into `sync.ExternalXUpdatedEvent`(s), and publishes them.
- `sync/events/external_order_updated.go` + `sync/handlers/order_updated_handler.go` + `sync/storage/order/order_pg.go` — the canonical pattern: an `ExternalXUpdatedEvent` carries a normalized `XInput`; the per-entity handler rebuilds the aggregate and enqueues it on the storage's buffered `InputChannel()`; the storage `Start` loop accumulates (`core/types/accumulator.go`, `batchSize=1000` / `1s` flush) and **bulk-upserts + writes the outbox integration event in one `UnitOfWork` transaction**. This decouples HTTP intake from the DB write — the high-concurrency property the pixel endpoint needs.

The NestJS reference (`/Users/gabrielaraujo/Desktop/Projetos/bk-company/bk-dash-backend/backend-old`) is the source of truth for pixel semantics: `webhooks/mappers/virtualStore/shopify/ShopifyPixelEventWebhookMapper/` (per-event sub-mappers + `extractUtmFromUrl`), and `internalEvents/handlers/PixelEvent/PixelCreatedHandler.ts` (the Redis per-visitor throttle in `canSaveEvent` + the 24h missing-stage backfill in `createRetroactiveEvents`).

## Problem

1. There is **no Go write path for pixel events**. The browser-side Shopify Pixel bundle has nowhere to POST: no ingest endpoint, no mapper, no persistence into the already-existing `tracking.pixel_events` table, and nothing publishes the already-existing `integration.shared.pixel_event.recorded` integration event. The TS funnel reader therefore queries an always-empty table.
2. Pixel ingest is **browser-origin and unsigned**, unlike every existing `/webhooks` flow (HMAC-verified). The intake path must accept it without a signature while staying idempotent and abuse-resistant under high volume.
3. Pixel platforms only emit *the event the visitor just triggered*. A visitor who lands directly on checkout produces a `CHECKOUT_COMPLETED` with no earlier `PAGE_VIEWED`/`PRODUCT_VIEWED` rows, so the funnel under-counts upper stages unless the missing earlier stages are **retroactively synthesized**.

## Goal

A merchant who installs the BK Dash pixel snippet starts producing funnel data: each browser pixel event is ingested through the same `/webhooks` endpoint (no signature, high-concurrency, non-blocking), normalized, persisted to `tracking.pixel_events`, and announced via `integration.shared.pixel_event.recorded` — so the existing TS funnel dashboard fills in, and Sales can later react to `CHECKOUT_COMPLETED`. Pixel becomes a first-class member of the `sync.external_*` event family rather than a bespoke subsystem, reusing the entire webhooks→sync pipeline.

## Decisions

1. **Pixel joins the `SyncEventName` union (additive contract amendment).** Add `EXTERNAL_PIXEL_EVENT_RECORDED: "sync.external_pixel_event_recorded"` to `wire/enums/sync-event-name.tsp` and regenerate Go + TS bindings (`bun sdk` / contracts codegen). This is the single contract change; it is additive and backward-compatible. The **output** integration event `integration.shared.pixel_event.recorded` already exists and is unchanged.

2. **Persistence lives in the `sync` BC**, mirroring `order`/`product`/`transaction` — not a new bounded context. New artifacts: `sync/events/external_pixel_event_recorded.go` (internal `ExternalPixelEventRecordedEvent` carrying a normalized `PixelEventInput` scoped by `storeIntegrationId` + `storeIntegrationExternalId` — **not** `storeId`, see Decision 3), `sync/handlers/pixel_event_recorded_handler.go`, a canonical `PixelEvent` struct with `NewPixelEventFromProviderInput` (`sync/entities/` or `sync/objects/`) that carries the server-resolved `storeId` for the row, and `sync/storage/pixel/` (channel-drain UPSERT into `tracking.pixel_events` + dual-write of the wire `PixelEventRecordedEvent`, in one `UnitOfWork` tx — same shape as `storage/order`). Writing the `tracking` schema from `sync` is consistent with `sync` already writing `sales.*` / `catalog.*`.

3. **Reuse `/webhooks` with a `type=PIXEL_EVENT` branch** (`Modify webhooks/controllers/webhook.go`). `type` defaults to the existing signed-webhook flow (unchanged). When `type=PIXEL_EVENT`: skip HMAC verification, fix `event = sync.external_pixel_event_recorded` (the browser bundle does not send the internal SyncEventName), require **only** `platform` + `storeIntegrationId` (the sales-channel id the bundle already embeds — `GetPixelScriptSnippet` injects `BKDASH_PIXEL_CONFIG.storeIntegrationId`), read the raw body, and save the existing `WebhookReceivedEvent` to the outbox (idempotent intake id `IDFromSeed("pixel-intake", platform, sha256(body))`), returning **202**. Downstream is the unchanged `WebhookReceivedHandler` → mapper-factory machinery.

   **The pixel event is scoped by the sales-channel integration, not by `storeId`.** The browser asserts only `platform` + `storeIntegrationId`; `storeId` is **never** a request param (a browser must not be able to attribute pixel traffic to an arbitrary store). The server resolves the sales-channel record — `integration.store_integrations` where `type=SALES_CHANNEL` — by `storeIntegrationId` to obtain `storeIntegrationExternalId` (`external_id`) and `storeId` (`store_id`). The internal `ExternalPixelEventRecordedEvent` then carries `storeIntegrationId` + `storeIntegrationExternalId` (the reference's `integrationSetHasVirtualStoreId` + provider external id); the persisted row's `storeId` (notNull on `tracking.pixel_events`, required by `GetPixelFunnel`) is the **server-resolved** value, denormalized onto the row.

4. **New cached Go sales-channel resolver** — `(storeIntegrationId) → {storeId, externalId, platform}` read directly from `integration.store_integrations` (single shared Postgres; `sync` already reads/writes cross-schema). The `credentials.Exchanger` is unsuitable: it returns only decrypted credentials (`map[string]string`), not the store/external ids, and routes through a TS HTTP call — a per-event round-trip would throttle a high-concurrency endpoint. Because the `(storeIntegrationId → storeId, externalId)` mapping is **immutable** (the id is a deterministic UUIDv5 of `(platform, externalId)`, and `storeId` never changes), the resolver memoizes in-process (cache-forever; cold miss does one indexed `SELECT ... WHERE id = $1`). A `storeIntegrationId` with no active sales-channel row → reject intake (`PIXEL_UNKNOWN_STORE_INTEGRATION`), no persist.

5. **One Shopify pixel mapper, keyed `(SHOPIFY, sync.external_pixel_event_recorded)`** (`webhooks/mappers/shopify/pixel_event_recorded.go`), registered in `webhooks/module.go`; other `SalesPlatform`s register as `PendingMapper`s (graceful `WEBHOOK_MAPPER_PENDING`). It switches on the Shopify pixel body's `name` to derive the `PixelEventType`, and extracts `visitorKey` (`clientId`), `occurredAt` (`timestamp`), `url`+`utm` (from `context.document.location.href` via the ported `extractUtmFromUrl`), `referrer`, `cartExternalId`, and `productExternalId`. The provider's native pixel event `id` becomes `externalEventId`. It emits exactly one `ExternalPixelEventRecordedEvent` per recognized body (unrecognized `name` → empty slice, mirroring the reference).

6. **Dedupe via deterministic id + `ON CONFLICT`.** Canonical row id = `IDFromSeed(platform, externalEventId)`, matching the locked `unique(platform, external_event_id)`. The storage UPSERTs `ON CONFLICT (id)`, so provider re-deliveries collapse.

7. **Redis per-visitor TTL throttle in the handler**, porting the reference `canSaveEvent`. Key = `pixel:{eventType}:{visitorKey}:{storeIntegrationId}`; per-type TTL — `PAGE_VIEWED` 60s, `PRODUCT_VIEWED` 300s, `PRODUCT_ADDED_TO_CART`/`PRODUCT_REMOVED_FROM_CART`/`CART_VIEWED`/`CHECKOUT_STARTED` 1800s, `CHECKOUT_COMPLETED`/`CHECKOUT_CONTACT_INFO_SUBMITTED` no throttle. A key seen within its TTL → drop the event (no persist, no publish). Redis is already available in api-go (`core/services/mediator/redis_mediator.go`).

8. **Live retroactive funnel backfill in the handler.** After the (throttled-surviving) incoming `PixelEvent` is built, query existing stages for its `visitorKey` within a **24h window** (new sync read query against `tracking.pixel_events`), then synthesize any canonical-order stages *before* the current one that are missing, and enqueue them on the same storage channel alongside the current event. Canonical stage order: `PAGE_VIEWED → PRODUCT_VIEWED → PRODUCT_ADDED_TO_CART → CART_VIEWED → CHECKOUT_STARTED → CHECKOUT_CONTACT_INFO_SUBMITTED → CHECKOUT_COMPLETED` (matching `GetPixelFunnel.FUNNEL_STAGE_ORDER`).

9. **Backfilled rows are normal rows with a deterministic synthetic `externalEventId`** (`synthetic:{visitorKey}:{stage}:{windowDay}`) — no `retroactive` column (the frozen table has none; we do not amend it). Repeat backfills collapse via `ON CONFLICT (id)`. A late-arriving *real* earlier event coexists with its synthetic twin, so a stage's raw `count` may slightly over-count, but `uniqueSessions` (distinct `visitorKey`) stays correct — and the funnel's robust metric is `uniqueSessions`. This matches the reference's accepted behavior.

10. **Out of scope.** The `sales.carts` Cart projection + `CartLinkedToOrderEvent` (separate spec — Sales reacting to `CHECKOUT_COMPLETED`); the bulk historical `SimulatePixel` seed tool; any non-Shopify pixel platform (registered as pending); and any TS-side change — the read path already ships and the sales-channel resolution is a Go-direct read (Decision 4), so no new TS endpoint is required.

## User Stories

- **Story 1 — merchant produces funnel data.** As a merchant who installed the pixel snippet, I want my storefront's pixel events captured, so the BK Dash funnel dashboard reflects real traffic.
  - Given a Shopify `checkout_completed` pixel body POSTed to `/webhooks?type=PIXEL_EVENT&platform=SHOPIFY&storeIntegrationId=…`, when the endpoint receives it, then it returns 202 without verifying a signature and (asynchronously) a `tracking.pixel_events` row exists with `eventType=CHECKOUT_COMPLETED`, the server-resolved `storeId` + `storeIntegrationExternalId`, the mapped `visitorKey`/`utm`/`cartExternalId`/`productExternalId`, and a `PixelEventRecordedEvent` is written to the outbox.
  - Given the same provider event id is delivered twice, when both are processed, then exactly one row exists (collapsed on `id`).
- **Story 2 — funnel stays consistent for direct-to-checkout visitors.** As a merchant, I want a visitor who only triggers a late funnel step to still count toward earlier stages, so drop-off math is meaningful.
  - Given a visitor's first-seen event is `CHECKOUT_STARTED` with no prior rows in 24h, when it is ingested, then synthetic `PAGE_VIEWED`, `PRODUCT_VIEWED`, `PRODUCT_ADDED_TO_CART` (and `CART_VIEWED`) rows for that `visitorKey` are also persisted.
  - Given backfill runs again for the same visitor and stage within the window, when it re-synthesizes, then no duplicate row is created (deterministic synthetic id collapses on conflict).
- **Story 3 — abuse/duplication resistance.** As an operator, I want rapid duplicate funnel steps from one visitor collapsed, so the funnel isn't inflated by a noisy client.
  - Given two `PAGE_VIEWED` events for the same `(visitorKey, storeIntegrationId)` arrive within 60s, when processed, then the second is dropped (not persisted, not published).
- **Story 4 — graceful platform coverage.** As a developer, I want unbuilt pixel platforms to fail soft.
  - Given a `(NUVEM_SHOP, sync.external_pixel_event_recorded)` body, when the handler resolves the mapper, then it returns `WEBHOOK_MAPPER_PENDING` (surfaced, not a 500), and no row is written.

## Acceptance Criteria

- [ ] AC-1: `wire/enums/sync-event-name.tsp` includes `EXTERNAL_PIXEL_EVENT_RECORDED: "sync.external_pixel_event_recorded"`; regenerated `wire.SyncEventName` (Go) and the TS binding expose it; the webhook controller's `event` `oneof` accepts it. All existing `SyncEventName` values are unchanged.
- [ ] AC-2: `POST /webhooks?type=PIXEL_EVENT&platform=SHOPIFY&storeIntegrationId=…` with a Shopify pixel body returns **202** with **no** signature header present, and saves exactly one `WebhookReceivedEvent` whose `event` is `sync.external_pixel_event_recorded`. Missing `platform` or `storeIntegrationId` → 400, no save. `storeId` is **not** an accepted param (rejected/ignored — never trusted from the client). The existing signed-webhook flow (`type` absent) is byte-for-byte unchanged (existing controller tests stay green).
- [ ] AC-3: The Shopify pixel mapper maps each of the 8 `PixelEventType` bodies to one `ExternalPixelEventRecordedEvent`, extracting `eventType`, `visitorKey`, `occurredAt`, `url`, `referrer`, `utm` (source/medium/campaign/term/content from the location href), `cartExternalId`, `productExternalId`, and `externalEventId` (provider event id). An unrecognized body `name` yields an empty result.
- [ ] AC-4: `PixelEventRecordedHandler` consuming `ExternalPixelEventRecordedEvent` results in a `tracking.pixel_events` UPSERT keyed on `id = IDFromSeed(platform, externalEventId)` and a `wire.PixelEventRecordedEvent` (`integration.shared.pixel_event.recorded`, `OwnerID = storeIntegrationId`, carrying `platform`, `storeIntegrationExternalId`, `eventType`, `cartExternalId`, `productExternalId`) written to the outbox — both in one `UnitOfWork` transaction. The row's `storeId` is the value resolved from the sales-channel record (Decision 4), never a client-supplied value. Re-delivery of the same provider event id leaves exactly one row.
- [ ] AC-9: The sales-channel resolver returns `{storeId, externalId, platform}` for a known `storeIntegrationId` (one indexed read, memoized on repeat); an unknown `storeIntegrationId` yields `PIXEL_UNKNOWN_STORE_INTEGRATION` and no row is written.
- [ ] AC-5: Given a visitor's earliest event in the 24h window is stage N (N > `PAGE_VIEWED`), the handler persists synthetic rows for every missing canonical stage `< N` for that `visitorKey`, each with `externalEventId = synthetic:{visitorKey}:{stage}:{windowDay}`; re-running backfill for the same visitor/stage/day creates no duplicate.
- [ ] AC-6: A second event of the same `eventType` for the same `(visitorKey, storeIntegrationId)` within that type's TTL is dropped (no row, no published event); after the TTL elapses it is processed normally. `CHECKOUT_COMPLETED` and `CHECKOUT_CONTACT_INFO_SUBMITTED` are never throttled.
- [ ] AC-7: A `(platform, sync.external_pixel_event_recorded)` pair without a real mapper resolves a `PendingMapper` and the handler returns `WEBHOOK_MAPPER_PENDING` (no 500, no row).
- [ ] AC-8: `bun tsc`, `go test ./...`, and `bun lint` are green; api-go boots with the new pixel storage drain goroutine registered in `sync/module.go`.

## Risks & Migration

- **No-`retroactive`-column over-count (accepted).** As in Decision 9, raw stage `count` can slightly exceed reality when a real earlier event arrives after its synthetic twin; `uniqueSessions` is unaffected. If precise `count` auditability is later required, it needs a `retroactive boolean` column (migration) + a frozen-contract amendment — explicitly deferred.
- **Backfill read-after-write gap.** Backfill reads committed `tracking.pixel_events`, but the triggering event is still in the storage channel when backfill runs. Backfill therefore computes missing stages from `DB existing stages ∪ {current event's stage}`, and enqueues synthetic + current together so the drain persists them in the same window. Idempotent synthetic ids make a duplicate backfill on the next event harmless.
- **Contract un-freeze.** Phase 0 was treated as frozen; this spec deliberately reopens `SyncEventName` for one additive value. The change is backward-compatible (no consumer breaks on an unknown-to-them name they don't subscribe to), but the regen must run before the Go mapper/controller compile against the new constant.

## Open Questions

- None blocking. The browser bundle (`GetPixelScriptSnippet` inlineScript) must POST `?type=PIXEL_EVENT&platform=SHOPIFY&storeIntegrationId=…` (no `storeId` — it is server-resolved per Decision 3/4) when the bundle ships — bundle itself is out of scope here.
