# Marketing Canonical Aggregates — Go Write-Side + TS Link Table — Design Spec

**Date:** 2026-05-28
**Status:** Approved
**Bounded Context:** `sync` (Go) + `marketing` (TS) + `bkdash_analytics`/`marketing` Drizzle schema
**Kind:** feature (Spec β — canonical aggregate model + link table)
**Story Points:** 13 — 6 new Go aggregates (entities + repos + Drizzle migration + idempotent UPSERT) ANDpolymorphic TS link table + 2 wire-event handlers + AdSpend → AdSpendManual rename + decomission TS Campaign write-side. Touches 2 bounded contexts + 1 Drizzle migration with no backfill; cross-service integration events already locked (Spec α); rubric tier-up applied for multi-BC + new projection-style read table.

## Context

Spec α (committed: c0e853c97 / 33b045f9c / 17af6d869) locked the Phase 0 wire-event contract for marketing: deleted 6 over-built `*Updated`/`*Recorded` events; added `MarketingBusinessAccountDiscoveredEvent` (new); added `businessAccountExternalId` denorm to `MarketingAdAccountDiscoveredEvent`; added `BusinessAccountStatus` + `AdAccountStatus` enums. The Go `sync` BC under `packages/api/go/internal/sync/` is the canonical write-authority for provider-synced entities — existing aggregates: `entities/order.go`, `entities/product.go`, `entities/product_variant.go`, `entities/transaction.go`. Each follows the same shape: private fields + separate `XInput` normalizer struct + `NewXFromProviderPayload` constructor for idempotent UPSERT via `Id.fromSeed(BK_DASH_NAMESPACE, platform, externalId, …)` PK. Drizzle migrations land under `packages/contracts/db/schema/sync.ts`.

The redirected model (chat 2026-05-28) extends the Go-write-side surface to the marketing hierarchy: `BusinessAccount`, `AdAccount`, `Campaign`, `AdSet`, `Ad`, `AdSpend` — all pure `(platform, externalId)`-keyed, no `integrationId` in aggregate state. Aggregates are **upserted by pipelines** (same handler pattern as `packages/api/go/internal/sync/handlers/order_updated_handler.go`: pipeline emits internal `ExternalXUpdated` Go event → handler builds aggregate + saves to storage drain). No Go-side projections from events.

On the TS side, the user's rule (chat 2026-05-28): events ONLY feed a polymorphic link table that bridges TS `StoreIntegration` (OAuth profile login) ↔ canonical Go aggregates by externalId. The existing `integration.MarketingAdAccount` aggregate (`packages/api/typescript/src/integration/entities/MarketingAdAccount.ts`) — per-(storeIntegrationId, externalId) row with `isSelected` — gets relocated into the new polymorphic table. TS marketing keeps `CampaignProductBinding` (manual user binding, TS-only concern) and MANUAL AdSpend (renamed `AdSpendManual` here). Existing TS `marketing.Campaign` write aggregate becomes dead code under the redirected model — reads route via SDK to Go.

## Problem

1. **No Go-side marketing aggregates exist yet.** The contract surface is locked (Spec α), but there are no entities/repos/migrations/handlers to receive a Facebook/Google/TikTok pipeline's normalized output. Spec γ+ (pipelines) can't ship without persistence.
2. **TS-side `integration.MarketingAdAccount` is a half-formed link table.** It's structured as a full aggregate (ID via `Id.fromSeed('marketing_ad_account', platform, externalId)` — note: hash doesn't include storeIntegrationId so two integrations discovering the same ad-account would collide; the per-row schema is keyed by `(storeIntegrationId, externalId)` which the hash can't enforce). It also lacks BusinessAccount-side rows, and lacks the user's required `active` / `validFrom` / `validTo` fields.
3. **TS-side `marketing.Campaign` and `marketing.AdSpend` AUTOMATIC branches are zombie code.** No wire-event handler populates them anymore (Spec α deleted `CampaignUpdated` + `AdSpendRecorded`). The TS aggregates compile but are write-orphaned for AUTOMATIC rows. The MANUAL branch of `AdSpend` is still valid — needs a clean rename to `AdSpendManual` to make the scope explicit.
4. **Reads of provider data from TS need an SDK route.** `GetCampaignsList`, `GetAdSpendBreakdown` currently query local TS Drizzle tables that won't be populated for AUTOMATIC data. They need to route through `Client.go.<...>()` SDK calls.

## Goal

Land the canonical Go-write-side aggregate model for marketing (BusinessAccount → AdAccount → Campaign → AdSet → Ad + AdSpend buckets), plus the polymorphic TS link table that bridges StoreIntegration → BM/AdAccount access, so Spec γ+ (Facebook/Google/TikTok pipelines) can be authored against a working persistence + projection layer. Decommission the dead TS-side marketing write-aggregates that no event populates.

## Decisions

1. **6 Go aggregates in `packages/api/go/internal/sync/entities/`**, one file each. All follow the existing pattern (private fields + `XInput` normalizer struct + `NewXFromProviderPayload` constructor + `Id.fromSeed(BK_DASH_NAMESPACE, platform, externalId, …)` deterministic PK):
   - `business_account.go` — fields: `id`, `platform: wire.MarketingPlatform`, `externalId`, `name`, `status: wire.BusinessAccountStatus`, `externalCreatedAt`, plus the standard `createdAt` / `updatedAt`. No `storeIntegrationId`.
   - `ad_account.go` — fields: `id`, `platform`, `externalId`, `businessAccountExternalId`, `name`, `currency: wire.CurrencyCode`, `timezone: string` (IANA), `status: wire.AdAccountStatus`, `externalCreatedAt`, standard timestamps.
   - `campaign.go` — fields: `id`, `platform`, `externalId`, `adAccountExternalId`, `name`, `status: wire.CampaignStatus`, `externalCreatedAt`, standard timestamps.
   - `ad_set.go` — fields: `id`, `platform`, `externalId`, `campaignExternalId`, `adAccountExternalId` (denorm for query-by-account), `name`, `status: wire.CampaignStatus`, `externalCreatedAt`, standard timestamps.
   - `ad.go` — fields: `id`, `platform`, `externalId`, `adSetExternalId`, `campaignExternalId` (denorm), `adAccountExternalId` (denorm), `name`, `status: wire.CampaignStatus`, `externalCreatedAt`, standard timestamps.
   - `ad_spend.go` — bucket aggregate: `id`, `platform`, `adAccountExternalId`, `campaignExternalId`, `currency: wire.CurrencyCode`, `startDate`, `endDate`, `groupBy: wire.AdSpendGroupBy`, `spendCents: int64`, standard timestamps. PK seed: `Id.fromSeed(BK_DASH_NAMESPACE, platform, adAccountExternalId, campaignExternalId, startDate, endDate, groupBy)` — idempotent on the exact bucket coordinates.
2. **Drizzle migration adds 6 tables under `packages/contracts/db/schema/sync.ts`**: `syncBusinessAccounts`, `syncAdAccounts`, `syncCampaigns`, `syncAdSets`, `syncAds`, `syncAdSpends`. Schema-qualified under `sync`. Each table has a deterministic `id uuid` PK + a `(platform, externalId)` unique index (where applicable; AdSpend uses the bucket key composite). Standard `createdAt` / `updatedAt` columns. Migration is additive — no backfill, no existing data.
3. **6 Go repositories in `packages/api/go/internal/sync/repositories/`**, one folder each: `businessaccount/`, `adaccount/`, `campaign/`, `adset/`, `ad/`, `adspend/`. Each has `XRepository` interface + `XPg` (pgx + sqlc) impl. Methods: `Find(ctx, id) (*X, error)`, `Save(ctx, x) error` (idempotent UPSERT on PK). No `FindByPlatformExternalID` — `Id.fromSeed` is deterministic, callers compute the ID and use `Find`. Following the existing `syncjob/syncjob_pg.go` pattern.
4. **6 internal Go events** in `packages/api/go/internal/sync/events/`: `external_business_account_updated.go`, `external_ad_account_updated.go`, `external_campaign_updated.go`, `external_ad_set_updated.go`, `external_ad_updated.go`, `external_ad_spend_recorded.go`. Each carries the corresponding `XInput` payload. Same pattern as the existing `external_order_updated.go`. These are Go-INTERNAL events (in-process mediator); they're NOT wire events.
5. **6 Go internal handlers** in `packages/api/go/internal/sync/handlers/`: one per `External*Updated` event. Each handler: receives the event, calls `entities.NewXFromProviderPayload(input)` to construct the aggregate (which validates the input), enqueues the aggregate to a storage drain channel for async persistence. Same pattern as the existing `order_updated_handler.go`.
6. **6 storage drain folders** under `packages/api/go/internal/sync/storage/`: `businessaccount/`, `adaccount/`, `campaign/`, `adset/`, `ad/`, `adspend/`. Each has a `Storage` struct with an input channel + a `Start(ctx) func()` that drains the channel in a goroutine and calls `repo.Save` for each entity. Same pattern as existing `storage/order/`.
7. **Two wire events also published from the Go side per discovery pipeline run** — `MarketingBusinessAccountDiscoveredEvent` (from the BUSINESS_ACCOUNTS pipeline) and `MarketingAdAccountDiscoveredEvent` (from the AD_ACCOUNTS pipeline). Published via the outbox-backed external mediator after each discovery enumerates the integration's accessible accounts. The TS handlers (Decision 11) consume these.
8. **One Drizzle table on the TS side: `packages/contracts/db/schema/marketing.ts`** adds `storeIntegrationMarketingAccess` (polymorphic). Columns: `id uuid (deterministic from storeIntegrationId+accessType+platform+externalId)`, `storeIntegrationId uuid not null`, `accessType varchar('BUSINESS_ACCOUNT'|'AD_ACCOUNT')`, `platform varchar (MarketingPlatform values)`, `externalId varchar`, `name varchar`, `parentExternalId varchar nullable` (for AD_ACCOUNT rows, denormalizes the parent BM externalId from the discovery event), `active boolean not null default false`, `validFrom date nullable`, `validTo date nullable`, standard `createdAt`/`updatedAt`. Unique index on `(storeIntegrationId, accessType, platform, externalId)`. **Schema qualified under `marketing`.**
9. **One TS aggregate: `marketing.StoreIntegrationMarketingAccess`** in `packages/api/typescript/src/marketing/entities/`. Schema-driven Zod aggregate carrying the columns above. Methods: `activate()` / `deactivate()` (flips `active`), `setValidityWindow(from?: Date, to?: Date)` (sets `validFrom`/`validTo`).
10. **One TS repository: `marketing.StoreIntegrationMarketingAccessRepository`** — interface + Drizzle impl + Mock. Methods: `findById(id)`, `findByStoreIntegrationAndExternalId(storeIntegrationId, platform, accessType, externalId)`, `save(entity)`, `listByStoreIntegration(storeIntegrationId, opts?: {accessType?, active?})`. Idempotent UPSERT on the composite unique.
11. **Two TS handlers in `packages/api/typescript/src/marketing/handlers/external.ts`**:
    - `OnMarketingBusinessAccountDiscovered` — receives `MarketingBusinessAccountDiscoveredEvent`. Computes the deterministic id via `Id.fromSeed('store_integration_marketing_access', storeIntegrationId, 'BUSINESS_ACCOUNT', platform, businessAccountExternalId)`; finds-or-creates the link row with `accessType=BUSINESS_ACCOUNT`, `parentExternalId=null`, `active=false`, `name=accountName`. Re-fires (subsequent discoveries) update `name` only.
    - `OnMarketingAdAccountDiscovered` — same pattern, `accessType=AD_ACCOUNT`, `parentExternalId=businessAccountExternalId`, `name=accountName`.
12. **Rename TS `marketing.AdSpend` → `marketing.AdSpendManual`**. Move file `packages/api/typescript/src/marketing/entities/AdSpend.ts` → `AdSpendManual.ts`; update all references (`RecordManualAdSpend`, `UpdateManualAdSpend`, `DeleteManualAdSpend`, `ManualAdSpendRecordedEvent`, `DrizzleAdSpendRepository` → `DrizzleAdSpendManualRepository`, `GetAdSpendBreakdown`, registry). The `adSpendType` discriminator field becomes unused — remove it; the aggregate is implicitly MANUAL by name. Drop the `AdSpendType` wire enum from `packages/contracts/wire/enums/ad-spend-type.tsp` (no longer needed; only MANUAL exists on TS side; AUTOMATIC lives in Go `sync.AdSpend`).
13. **Decommission TS `marketing.Campaign` write aggregate.** Delete `packages/api/typescript/src/marketing/entities/Campaign.ts` + `CampaignRepository/` folder + tests + `GetCampaignsList.ts` use case + `getCampaignsList` controller. `CampaignProductBinding` references `campaignExternalId` (not the local Campaign aggregate ID); keep as-is. `BindCampaignToProduct` / `UnbindCampaignFromProduct` keep working since they only need `campaignExternalId` (provider's id), not a local Campaign row.
14. **Delete the corresponding Drizzle table** `marketingCampaigns` in `packages/contracts/db/schema/marketing.ts`. Migration drops the table — additive in spirit but destructive of any local rows; since no Go-side or TS-side handler populates this AUTOMATIC table, any existing rows were stale dev data — accept the drop.
15. **Migration sequencing**: Drizzle migration #1 (Go side, sync schema additions: 6 new tables) + Drizzle migration #2 (TS side, marketing schema: add `storeIntegrationMarketingAccess`, drop `marketingCampaigns`). Generate via `bun migrate:create` per migration. Run via `bun migrate:dev`.
16. **No SDK regeneration in this spec.** Spec α already locked the wire contract; this spec only adds Go repos + TS aggregates that consume the existing generated bindings.
17. **`integration.MarketingAdAccount` aggregate is deleted** (`packages/api/typescript/src/integration/entities/MarketingAdAccount.ts` + test + any usage). It's superseded by the polymorphic `storeIntegrationMarketingAccess` link in marketing BC. Grep audit will surface consumers; expect zero or near-zero hits (this was a forward-projection that never gained users).
18. **The `MockMarketingAdAccountDiscoveredEventBuilder` (or similar test fixture) gets a sibling for BusinessAccount discovery** — `MockMarketingBusinessAccountDiscoveredEventBuilder` — so TS handler tests can build typed event payloads.

## User Stories

- **Story 1 — Facebook pipeline can persist a BusinessAccount.** As a developer authoring the Facebook BUSINESS_ACCOUNTS pipeline (Spec γ Facebook), I want to call `entities.NewBusinessAccountFromProviderPayload(input)` → publish internal `ExternalBusinessAccountUpdated` → handler → storage drain → Postgres row, so the canonical BM survives across runs and re-runs idempotently. *(AC-1, AC-2, AC-3, AC-4)*
  - Given a clean DB, when the pipeline normalizes a Facebook BM and emits the internal event, then a `sync.business_accounts` row appears with the deterministic id from `Id.fromSeed`.
  - Given the same BM re-arrives on the next run, when the pipeline emits again, then the row is UPDATED in place (name change captured) — no duplicate row, no error.

- **Story 2 — TS link table records which integrations have access to which BMs / AdAccounts.** As a developer about to render the merchant's marketing-account picker, I want one wire event per (integration, BM) discovery and one per (integration, AdAccount) discovery to populate a single polymorphic link table, so the picker can list all accessible accounts with `active`/`validFrom`/`validTo` per row. *(AC-5, AC-6, AC-7)*
  - Given a Facebook integration completes its BUSINESS_ACCOUNTS pipeline, when the BM discovery wire event lands on TS, then `marketing.store_integration_marketing_access` has a row with `accessType=BUSINESS_ACCOUNT`, `active=false`, `name=<provider name>`.
  - Given the AD_ACCOUNTS pipeline then runs, when its AdAccount discovery wire events land, then each row has `accessType=AD_ACCOUNT` and `parentExternalId=<the parent BM externalId>` allowing the picker to group ad-accounts under their BM.

- **Story 3 — Manual AdSpend keeps working under the new name.** As a developer maintaining the MANUAL ad-spend write flow, I want the TS aggregate renamed to `AdSpendManual` and the AUTOMATIC branch removed, so the scope of the write aggregate is unambiguous and no broken handler tries to project AUTOMATIC rows. *(AC-9, AC-10)*
  - Given a merchant submits a manual ad-spend form, when `RecordManualAdSpend` runs, then a row is written via `DrizzleAdSpendManualRepository` with the same DB shape as before (column-level migration is column rename only; existing rows preserved if any).

- **Story 4 — Provider campaign reads route via SDK.** As a developer rendering the campaigns picker for the CampaignProductBinding form, I want `GetCampaignsList` to call `Client.go.listCampaigns({adAccountExternalId})` via the SDK instead of querying the local TS `marketing.campaigns` table (now deleted), so reads reflect the canonical Go-side data. *(AC-11)*
  - Note: the Go-side `GetCampaignsList` SDK endpoint is a Spec γ concern (Facebook Campaign pipeline + its read controller). For this spec, document the migration but the TS `GetCampaignsList` is reduced to a stub that returns an empty list with a TODO; the binding flow stays functional because `BindCampaignToProduct` only needs an externalId string, not a Campaign row lookup.

## Open Questions

1. **AdSpend Drizzle PK strategy.** The composite `(platform, adAccountExternalId, campaignExternalId, startDate, endDate, groupBy)` is wide; the `Id.fromSeed` hash collapses it to a single uuid. Use the uuid as PK + add a composite unique on the source fields for accident-prevention? Or just rely on the uuid (trusting `Id.fromSeed` determinism)? Recommendation: uuid PK only; deterministic id IS the de-dupe mechanism — adding a composite unique is redundant.
2. **Pre-Spec γ smoke for the Go aggregates.** Without pipelines, the only way to exercise the aggregates is unit + repo tests + handler tests. We could add a tiny end-to-end test that crafts an `XInput` manually, runs it through the handler, and asserts the storage drain row — coverage parity with `order_updated_handler_test.go`. Recommendation: include such a test per aggregate (AC-4 covers it).
3. **`integration.MarketingAdAccount` cascading deletes.** The current `MarketingAdAccount.ts` aggregate has tests + may be referenced by integration handlers (`IntegrationActivatedHandler`, `TriggerReintegration`). Decision 17 says delete; need to audit those references during T-AC-8 and refactor or delete each.
