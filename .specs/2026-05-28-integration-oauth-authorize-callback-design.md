# Integration OAuth Authorize + Callback — Design Spec

**Date:** 2026-05-28
**Status:** Approved
**Bounded Context:** integration
**Kind:** feature
**Story Points:** 5 — single context end-to-end; 2 new HTTP routes + 1 new use case + 1 new HMAC service + per-platform `AuthorizeUrlBuilder` abstract/factory with 4 real impls + 4 new error codes; no migration, no projection, no event, no cross-service contract.

## Context

The `integration` bounded context (`packages/api/typescript/src/integration/`) owns connecting a merchant's external platforms (Shopify, Meta Ads, Google Ads, NuvemShop, plus several manual/credential platforms). Today the **back half** of OAuth is fully wired: the `ConnectIntegration` use case (`packages/api/typescript/src/integration/usecases/ConnectIntegration.ts`) takes `{ oauthCode, credentials }`, runs `OAuthCodeExchanger.exchange()` (real impls under `services/{shopify,meta,google-ads,nuvemshop}/`), seals tokens in the `CredentialVault`, gates on `HandshakeService.handshake()` (Shopify is the only real impl today; the just-completed refactor made it a pure throw-or-resolve gate), persists `StoreIntegration` + `IntegrationCredentialSecret`, and emits `IntegrationConnectionInitiated → HandshakeSucceeded → Activated`. The use case is reached via `POST /integrations` (`controllers/ConnectIntegrationController.ts`), which expects the frontend to already hold the OAuth code.

The **front half** does not exist. There is no endpoint that builds the provider's authorize URL, no controller that receives the provider's OAuth redirect, no `state` token issuance/verification, and no per-platform metadata for `client_id` / `redirect_uri`. The frontend has no integrations UI yet either (`packages/app/react/src/routes/(app)/` only has `dashboard/`), so this gap has been latent — but any "Login with Shopify" button is blocked on it.

Two existing patterns in this codebase carry the design: (1) `tenancy/services/InvitationTokenService.ts` mints HMAC-signed envelopes via `createHmac('sha256', Config.env.JWT_SECRET)` + `timingSafeEqual` — the exact shape we want for `state`; (2) `tenancy/controllers/AcceptInvitation.ts` is the analog "public but token-authenticated" controller (no `AuthAccountMiddleware`; the signed token IS the auth). The per-platform descriptor files (`services/shopify/ShopifyDescription.ts`) already hold scopes and credential schemas, so the authorize URL builder reads from there rather than redeclaring scopes.

The existing `OAuthCodeExchangerFactory` + `HandshakeServiceFactory` (under `services/{OAuthCodeExchanger,HandshakeService}/`) set the per-platform factory pattern this spec mirrors for `AuthorizeUrlBuilder`.

## Problem

1. **No authorize URL endpoint.** The frontend cannot get the URL to redirect the user to. Provider authorize URLs are non-trivial (Shopify embeds the shop domain in the host; Google requires `access_type=offline` + `prompt=consent` for refresh tokens; Meta needs `config_id` or scope; NuvemShop's URL embeds the app id in the path), so the frontend cannot build them client-side without leaking client ids and re-implementing per-provider quirks.
2. **No callback endpoint.** Providers redirect the browser to a `redirect_uri` you pre-registered with them. Nothing in the codebase receives `?code&state` from the provider. Today the OAuth code can only reach `ConnectIntegration` if the frontend somehow already has it — which is impossible without (1).
3. **No CSRF defense.** OAuth `state` is the standard binding between the authorize request and the callback. Without it, a callback hitting our server cannot be tied to the user/store who initiated.
4. **Connect endpoint over-exposes its OAuth branch.** `POST /integrations` accepts `connectionMode: OAUTH` with a raw `oauthCode` body field — meaning even after the callback exists, a misbehaving or compromised frontend could POST an arbitrary code, bypassing the state binding. The schema admits a leaf that nothing should reach via HTTP.

## Goal

A store owner clicks "Login with Shopify" (or Meta / Google Ads / NuvemShop), is redirected to the provider, grants access, and lands back on `/app/integrations` with a persisted, active `StoreIntegration` for that platform — without the OAuth code, client secret, or any intermediate token ever touching the browser. The backend deliverable is the two HTTP routes and the supporting services; the frontend route(s) ship in a separate spec.

## Decisions

1. **Two new HTTP routes.** `POST /integrations/oauth/authorize` (authenticated; `AuthAccountMiddleware + RequireStoreMember + RequireStoreRole([OWNER, ADMIN])` — same triad as `ConnectIntegrationController`). `GET /integrations/oauth/callback/:platform` (public; no auth middleware — the `state` token IS the auth, analog to `tenancy/controllers/AcceptInvitation.ts`).
2. **State is a stateless HMAC envelope.** New `OAuthStateTokenService` in `integration/services/OAuthStateTokenService.ts` mirroring `InvitationTokenService`: `${base64url(JSON.stringify(payload))}.${sig}` where `sig = HMAC-SHA256(Config.env.JWT_SECRET, b64payload).digest('base64url')`. Verification uses `timingSafeEqual`. **TTL = 300 seconds (5 minutes).** No DB row, no migration, no repository.
3. **State payload is platform-uniform.** `{ userId, storeId, type, platform, identifier?, nonce, exp }`. `identifier` is the pre-handshake identifier the platform needs to build its authorize URL — present for platforms that need it (Shopify: the `.myshopify.com` domain), absent for platforms whose identifier is only discovered post-token-exchange (Meta business id, Google customer id, NuvemShop store id). `nonce` is `crypto.randomUUID()` so two concurrent authorize requests for the same `(user, store, platform)` mint distinct tokens.
4. **State is bound to the callback URL's platform.** `OAuthStateTokenService.verify(state, { expectedPlatform })` throws `OAUTH_STATE_PLATFORM_MISMATCH` if the path-param platform differs from the payload's platform. This means a state minted for Shopify cannot be replayed at the Meta callback even if someone misregistered redirect URIs.
5. **Per-platform callback paths, not a single multiplexed endpoint.** `GET /integrations/oauth/callback/:platform` where `:platform` ∈ `{ shopify, meta, google_ads, nuvem_shop }` (lower-snake; controller maps to `SalesPlatform.SHOPIFY` etc.). The platform identity comes from the path the provider was told to redirect to — not from query data we'd have to parse before verifying. If `state` is missing or malformed we still know which provider sent us.
6. **Redirect URIs are derived, not configured.** Each provider's `redirect_uri` = `${Config.env.API_URL}/integrations/oauth/callback/${platformPathSegment}`. Computed in one place (the `AuthorizeUrlBuilder` base or a small helper); never an env var. Single source of truth; no drift between what we register on provider dashboards and what we send.
7. **`AuthorizeUrlBuilder` abstract + factory, mirroring the existing per-platform service pattern.** New folder `integration/services/AuthorizeUrlBuilder/` with `AuthorizeUrlBuilder.ts` (abstract: `readonly type`, `readonly platform`, `abstract build(input: { identifier?: string; state: string }): string`), `AuthorizeUrlBuilderFactory.ts` (constructor-injected per-platform builders, nested record keyed by `(type, platform)`, throws `PLATFORM_NOT_SUPPORTED`), and `MockAuthorizeUrlBuilder.ts` for tests. Four real impls under their existing platform folders: `services/shopify/ShopifyAuthorizeUrlBuilder.ts`, `services/meta/MetaAuthorizeUrlBuilder.ts`, `services/google-ads/GoogleAdsAuthorizeUrlBuilder.ts`, `services/nuvemshop/NuvemShopAuthorizeUrlBuilder.ts`. Each owns its provider's URL shape and reads scopes from its sibling `*Description.ts`.
8. **App-level OAuth credentials live in `Config.env`.** Four new env vars: `SHOPIFY_APP_CLIENT_ID` + `SHOPIFY_APP_CLIENT_SECRET`, `META_APP_CLIENT_ID` + `META_APP_CLIENT_SECRET`, `GOOGLE_ADS_CLIENT_ID` + `GOOGLE_ADS_CLIENT_SECRET`, `NUVEMSHOP_APP_CLIENT_ID` + `NUVEMSHOP_APP_CLIENT_SECRET` (all default `undefined`). The integration registry binds each per-platform builder + the existing per-platform exchanger to the matching Config pair (the exchanger's `{ clientId, clientSecret }` constructor is the existing wiring point).
9. **Callback calls `ConnectIntegration` in-process via DI.** The callback controller resolves `ConnectIntegration` from the container and invokes `.execute({...})` directly. The frontend never sees the OAuth code. The per-platform mapping from state's `identifier` to `ConnectIntegration.credentials` lives on the descriptor — each `*Description.ts` exports a `credentialKeyForIdentifier` (e.g. `'shopDomain'` for Shopify, `null` for the others) so the callback writes `credentials: identifier !== undefined ? { [key]: identifier } : {}`.
10. **`POST /integrations` narrows to non-OAuth modes.** The existing `ConnectIntegrationBodySchema` in `integration/services/index.ts` is rebuilt to admit only the `MANUAL` and `CREDENTIALS` leaves of the platform connect union. The OAuth leaf becomes physically unreachable via HTTP — TS rejects it at the schema, no runtime branch. This is a breaking change to the generated SDK but currently safe (no frontend caller uses the OAuth leaf yet).
11. **New `AuthorizeIntegration` use case.** `integration/usecases/AuthorizeIntegration.ts` orchestrates: validate `(type, platform)` is OAuth-supported via `AuthorizeUrlBuilderFactory.has(platform)` (throws `PLATFORM_NOT_SUPPORTED` if not); mint state via `OAuthStateTokenService.generate({ userId, storeId, type, platform, identifier?, ttlSec: 300 })`; build URL via the per-platform builder; return `{ authorizeUrl, state, expiresAt }`. No DB writes, no events, no transaction.
12. **Callback maps every `BaseError` to an error redirect.** The callback controller wraps verify + ConnectIntegration in `tryCatchAsync`. On success: `302 ${Config.env.APP_URL}/app/integrations?status=ok&storeIntegrationId=<id>&platform=<platform>`. On error: `302 ${Config.env.APP_URL}/app/integrations?status=error&code=<BaseError.name>&platform=<platform>`. **Never a JSON 4xx** — the browser is mid-redirect; a JSON response would surface as a broken page. The frontend reads `?code` and maps to an i18n key (frontend concern; out of scope).
13. **New error codes in `integration/errors/index.ts`.** Added to `IntegrationApplicationErrors`: `OAUTH_STATE_INVALID`, `OAUTH_STATE_EXPIRED`, `OAUTH_STATE_PLATFORM_MISMATCH`, `OAUTH_USER_DENIED`. The first three are thrown by `OAuthStateTokenService.verify`; the fourth is thrown by the callback when the provider redirect carries `?error=access_denied` (and no `code`).
14. **Out of scope.** No migration, no projection, no domain or integration event (the existing `ConnectIntegration` event triplet still emits). No token refresh use case (refresh tokens are persisted by exchangers but no refresher ships here). No webhook auto-registration after Connect succeeds. No frontend routes. No multi-store cross-binding — `storeId` in state means a state minted in store A cannot connect for store B.

## User Stories

- **Store owner connects Shopify.** As a store owner, I want to connect my Shopify store via OAuth so that the integration is active without me copy-pasting tokens.
  - Given I'm signed in with `STORE_OWNER` (or `ADMIN`) on store S, when I `POST /integrations/oauth/authorize { type: SALES_CHANNEL, platform: SHOPIFY, identifier: 'acme.myshopify.com' }`, then I receive `{ authorizeUrl: 'https://acme.myshopify.com/admin/oauth/authorize?...&state=<token>', state, expiresAt }`.
  - Given my browser is redirected to `authorizeUrl` and I grant access, when the provider 302s to `GET /integrations/oauth/callback/shopify?code=<code>&state=<token>`, then the backend 302s to `${APP_URL}/app/integrations?status=ok&storeIntegrationId=<id>&platform=SHOPIFY` and a `StoreIntegration` row exists for `(S, SHOPIFY)` with `active = true` and the expected event triplet persisted.

- **Store owner connects Google Ads.** As a store owner, I want to connect Google Ads via OAuth without supplying any identifier up front (Google discovers my customer id from the token).
  - Given I'm signed in, when I `POST /integrations/oauth/authorize { type: MARKETING, platform: GOOGLE_ADS }` (no `identifier`), then I receive an `authorizeUrl` containing `access_type=offline`, `prompt=consent`, and the descriptor's scopes — with our derived `redirect_uri`.
  - Given the provider 302s back with `?code&state`, when the callback runs, then `ConnectIntegration` is invoked with `credentials: {}` and the exchanger resolves the customer id.

- **Owner clicks Deny at the provider.** Given the provider 302s back to `GET /integrations/oauth/callback/:platform?error=access_denied&state=<token>` (no `code`), when the callback runs, then it 302s to `${APP_URL}/app/integrations?status=error&code=OAUTH_USER_DENIED&platform=<platform>` and no `StoreIntegration` row is created.

- **Stale state.** Given I started authorize >5 minutes ago, when I land at the callback, then the state verify throws `OAUTH_STATE_EXPIRED` and the callback 302s to the error variant with `code=OAUTH_STATE_EXPIRED`.

- **Tampered state.** Given an attacker rewrites the `state` query param, when the callback verifies the HMAC, then `timingSafeEqual` fails and the callback 302s with `code=OAUTH_STATE_INVALID`.

- **Platform mismatch.** Given a state was minted for `SHOPIFY`, when it arrives at `GET /integrations/oauth/callback/meta?code&state`, then verify throws `OAUTH_STATE_PLATFORM_MISMATCH` and the callback 302s with that code.

- **Handshake fails inside callback.** Given the OAuth code exchange succeeds but the Shopify handshake fails (e.g., missing scope), when the callback runs, then `ConnectIntegration` throws `INTEGRATION_INSUFFICIENT_SCOPES`, no row is persisted (existing use case behavior), and the callback 302s with `code=INTEGRATION_INSUFFICIENT_SCOPES`.

- **FE attempts OAuth via the public Connect endpoint.** As a developer, I want `POST /integrations` to refuse OAuth bodies at the schema layer so that the callback is the only path to OAuth-mode connection.
  - Given I `POST /integrations { connectionMode: OAUTH, ... }`, when the controller validates the body, then the request fails with `VALIDATION_ERROR` because the OAuth leaf is no longer in the schema.

## Acceptance Criteria

- [ ] AC-1: `POST /integrations/oauth/authorize` returns `{ authorizeUrl: string, state: string, expiresAt: number }` for each of the four supported platforms (Shopify, Meta, Google Ads, NuvemShop) and throws `PLATFORM_NOT_SUPPORTED` for any other `(type, platform)` pair.
- [ ] AC-2: `POST /integrations/oauth/authorize` requires `AuthAccountMiddleware + RequireStoreMember + RequireStoreRole([OWNER, ADMIN])` — a STAFF-role membership receives `UNAUTHORIZED`.
- [ ] AC-3: The minted `state` token is HMAC-SHA256-verifiable with `Config.env.JWT_SECRET`; flipping any byte fails `timingSafeEqual` and `verify` throws `OAUTH_STATE_INVALID`.
- [ ] AC-4: A state token with `exp` in the past (>300s old) throws `OAUTH_STATE_EXPIRED` on verify.
- [ ] AC-5: A state token whose payload `platform` differs from the verify-time `expectedPlatform` throws `OAUTH_STATE_PLATFORM_MISMATCH`.
- [ ] AC-6: `GET /integrations/oauth/callback/shopify?code&state` (happy path) calls `ConnectIntegration.execute({ connectionMode: OAUTH, type, platform, credentials: { shopDomain: <identifier from state> }, oauthCode: code, storeId, userId })` and 302s to `${Config.env.APP_URL}/app/integrations?status=ok&storeIntegrationId=<uuid>&platform=SHOPIFY` with HTTP 302 and a `Location` header.
- [ ] AC-7: `GET /integrations/oauth/callback/google_ads?code&state` (no identifier in state) calls `ConnectIntegration.execute({ ..., credentials: {} })` — the exchanger resolves the identifier post-token.
- [ ] AC-8: `GET /integrations/oauth/callback/:platform?error=access_denied&state` 302s with `?status=error&code=OAUTH_USER_DENIED&platform=<platform>` and does not invoke `ConnectIntegration`.
- [ ] AC-9: Any `BaseError` thrown inside the callback (`OAUTH_STATE_INVALID` / `OAUTH_STATE_EXPIRED` / `OAUTH_STATE_PLATFORM_MISMATCH` / `INTEGRATION_HANDSHAKE_FAILED` / `INTEGRATION_INSUFFICIENT_SCOPES` / `INTEGRATION_ALREADY_CONNECTED` / `OAUTH_CODE_EXCHANGE_FAILED`) is translated to `?status=error&code=<BaseError.name>&platform=<platform>` via 302 — never a JSON 4xx.
- [ ] AC-10: `POST /integrations` with `body.connectionMode === 'OAUTH'` fails with `VALIDATION_ERROR` — the OAuth leaf has been removed from `ConnectIntegrationBodySchema`.
- [ ] AC-11: For each of the four platforms, the built authorize URL contains the provider-mandated params: Shopify (`client_id`, `scope`, `state`, `redirect_uri`, host is `https://{identifier}/admin/oauth/authorize`); Google Ads (`client_id`, `scope`, `state`, `redirect_uri`, `response_type=code`, `access_type=offline`, `prompt=consent`); Meta (`client_id`, `scope`, `state`, `redirect_uri`, `response_type=code`); NuvemShop (`client_id` embedded in path per provider spec, `state`).
- [ ] AC-12: The redirect URI sent in each authorize URL equals `${Config.env.API_URL}/integrations/oauth/callback/${platformPathSegment}` — verified by parsing the URL and reading the `redirect_uri` param (or, for NuvemShop, by reading the provider's documented field).
- [ ] AC-13: The callback creates exactly the same `StoreIntegration` + `IntegrationCredentialSecret` rows + `IntegrationConnectionInitiated / HandshakeSucceeded / Activated` events as the legacy in-process `ConnectIntegration` happy path (regression coverage — confirms no behavior drift from the topology change).

## Open Questions

None at write time. If any provider's authorize URL has a quirk not captured here (e.g., NuvemShop's path-embedded `client_id` shape), the per-platform `AuthorizeUrlBuilder` impl absorbs it without changing the cross-cutting design.

## Risks & Migration

- **SDK breaking change.** `POST /integrations` no longer accepts `connectionMode: OAUTH`. Currently safe — no frontend caller uses it (no `/app/integrations` route exists yet, and `grep` for `useConnectIntegration` in `packages/app/react/src/` returns nothing). After this lands, regenerate the SDK (`bun sdk`) and confirm `tsc` stays green; any FE caller that appears later that wants OAuth must go through the authorize/callback flow.
- **Provider dashboard registration.** Each provider's developer console must register `${API_URL}/integrations/oauth/callback/${platform}` as an authorized redirect URI before that platform can be tested end-to-end. This is operational, not code — but the spec ships dead until those entries exist.
- **Env vars.** Eight new vars (4 client_id + 4 client_secret) need to land in `.env.example` and any deployment config. Missing values surface as `OAUTH_CODE_EXCHANGE_FAILED` from the existing exchanger (the per-platform exchangers already validate constructor input).
