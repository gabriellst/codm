```
READY_AFTER_S=2

```

- `RSS_MEDIAN_KB=337712` (~330 MiB) — daemon TS + PGlite embarcado, em regime.
- `DATA_DIR_KB=28256` (~27.6 MiB) — `du -sk` do data dir PGlite recém-migrado, sem carga.

Shutdown limpo observado no mesmo run (`HTTP server stopped` → `OutboxDispatcher stopped` →
`Database connections closed`), ou seja o número é de um processo saudável, não de um que morreu
no meio.

## Notas de leitura

- O RSS acima é o **teto a bater**: a decisão (a) troca PGlite (WASM + heap do Postgres embarcado)
  por `@libsql/client` (addon nativo). Uma regressão de RSS depois do flip é sinal de que algo
  ficou carregado à toa, não de ruído de medição — as três amostras variam <1.2%.
- `DATA_DIR_KB` mede o **substrato antigo**. Depois do flip o data dir passa a ser o mesmo
  `codedm.db` do gateway Go, e a comparação relevante deixa de ser dir-vs-dir e vira
  arquivo-vs-dir. Registrado aqui só para que a comparação seja possível.

### Dois ACs de T07 estão ERRADOS para este workspace — medido, não inferido

O plano pede `test -d node_modules/@libsql` e `test -d node_modules/libsql`. **Os dois falham**
neste checkout, e não porque a dependência esteja ausente:

```
$ test -d node_modules/@libsql ; echo $?   → 1
$ test -d node_modules/libsql  ; echo $?   → 1
$ ls -d node_modules/.bun/@libsql+client@*/node_modules/@libsql/client
node_modules/.bun/@libsql+client@0.17.4/node_modules/@libsql/client
$ ls -d node_modules/.bun/libsql@*/node_modules/libsql
node_modules/.bun/libsql@0.5.29/node_modules/libsql
$ ls -ld packages/api/typescript/core/node_modules/@libsql/client
… -> ../../../../../../node_modules/.bun/@libsql+client@0.17.4/node_modules/@libsql/client
```

Este workspace usa o layout **isolado** do bun (`node_modules/.bun/<pkg>@<ver>/…` + symlink no
`node_modules` de cada workspace), não o hoisted estilo npm que os dois ACs presumem. Um pacote
correta e completamente instalado simplesmente **não** aparece em `node_modules/<nome>` na raiz.
Escritos como estão, os dois ACs reprovariam a execução certa.

Forma corrigida — o que o plano de fato quer asseverar (o wrapper resolve **e** o addon nativo
está lá, não só o JS), por **resolução/comportamento** em vez de por caminho de layout:

```
test -d packages/api/typescript/core/node_modules/@libsql/client
test "$(ls -d node_modules/.bun/libsql@*/node_modules/libsql | wc -l | tr -d ' ')" -ge 1
# decisivo: abrir um arquivo local EXIGE o addon nativo — JS puro não faz isso
( cd packages/api/typescript/core && bun -e "…createClient({url:'file:…'})…" ) | grep -q NATIVE_ADDON_OK
```

Rodado: `NATIVE_ADDON_OK 42` (CREATE TABLE + INSERT + SELECT num arquivo temporário).

### Um terceiro AC é VÁCUO — `bun --print` engole o erro

```
$ bun --print "require('@libsql/client/package.json').version"
undefined                      # exit 0
```

O `exports` do pacote não expõe `./package.json`; o bun devolve `undefined` **e sai 0**, em vez de
lançar. O AC seguinte é `test -n "$RESOLVED"`, e a string `"undefined"` é não-vazia — ou seja o
critério passa com a versão nunca tendo sido lida. Forma corrigida, que devolve o valor de verdade:

```
RESOLVED="$(bun --print "JSON.parse(require('fs').readFileSync(require.resolve('@libsql/client/package.json'),'utf8')).version")"   → 0.17.4
```
