**Context.** template sellers buy inventory from external suppliers. Today none of that is modeled. We are adding a **Procurement** capability so a seller can place a purchase order with a supplier, and so the platform can track the inbound shipment that fulfils it as the supplier's system pushes status webhooks (created → packed → in_transit → delivered). The same webhook stream also drives a per-supplier on-time-delivery scorecard the seller sees on a dashboard. A Go sync worker already owns every other external-webhook ingestion pipeline in this repo (it runs the normalizer/pipeline/channel layout); the TS backend owns BFF reads and seller-issued commands. There is no reference supplier-system checkout on disk to mirror — derive shapes from THIS spec.
**Problem.** Sellers reconcile supplier deliveries by hand across spreadsheets and supplier emails; ~3 hrs/week per seller, and late suppliers are invisible until stockouts.
**Goal.** A seller places a purchase order, watches its inbound shipment advance live as supplier webhooks arrive, and sees a per-supplier on-time scorecard.
**Decisions (HOW — frozen).** - D1. A **PurchaseOrder** is seller-issued (a command), has a lifecycle
  (DRAFT → PLACED → RECEIVED → CLOSED / CANCELLED) and line items, each line a
  quantity + a unit cost as money (cents + currency). It guards "cannot receive more
  than ordered" and "cannot cancel after RECEIVED".
- D2. Supplier delivery **status webhooks** are ingested by the Go sync worker:
  `Controller → Mapper(factory by supplier platform) → IntegrationEvent → outbox →
  Handler`. The webhook delivery itself is a fact-that-happened, deduplicated by a
  partial unique index — it is NOT a seller-issued command.
- D3. The seller's dashboard needs (a) a live inbound-shipment timeline per order and
  (b) a per-supplier on-time-delivery scorecard (delivered-on-time / total, rolling).
  Both are read shapes the seller polls a screen for; the scorecard aggregates across
  many shipments per supplier.
- D4. Supplier platforms in scope: a fixed closed set the seller picks from when
  registering a supplier connection. The connection mode is one of OAUTH /
  CREDENTIALS / MANUAL.
- D5. The plan ships under a SINGLE PR; the seller-facing screens are a React route
  with a live-updating timeline component and a scorecard component.

**User Stories.** - US-1: As a seller I place a purchase order with line items so the supplier fulfils
  it.
- US-2: As a seller I cancel a not-yet-received purchase order so I stop an order I no
  longer need.
- US-3: As a seller I watch the inbound shipment advance live as the supplier reports
  progress, so I know when stock arrives without emailing them.
- US-4: As a seller I see a per-supplier on-time-delivery scorecard so I can drop
  chronically-late suppliers.

**Acceptance Criteria.** - AC-1: Placing an order with valid lines persists it as PLACED and emits a
  domain event.
- AC-2: Cancelling a RECEIVED order is rejected with a typed domain error. - AC-3: A `delivered` supplier webhook advances the matching inbound-shipment read
  model and the seller's timeline reflects it without a manual refresh.
- AC-4: The scorecard recomputes a supplier's on-time ratio when a new delivery
  webhook lands.
