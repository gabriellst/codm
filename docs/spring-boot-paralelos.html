1 A linha lógica — uma operação do começo ao fim

Um único request, POST /catalog/products, percorre esta cadeia. Os passos 1→4 rodam dentro de uma transação (síncrono). Do 5 em diante é assíncrono: o evento foi gravado junto com a entidade e é despachado depois do commit.

1–4 síncrono (1 transação) 5–6 evento (pós-commit) 7–8 efeitos
  1. Controller — recebe o request, valida o corpo e chama o use case.
  2. Use Case — abre a transação e orquestra (não contém regra de negócio).
  3. Entidade — valida as invariantes, muda de estado e levanta o evento.
  4. Repositório — grava a entidade e o evento na mesma transação (outbox).
  5. Evento — o fato ("produto criado"), tipado, agora guardado no outbox.
  6. Disparo — depois do commit, o outbox entrega o evento aos assinantes.
  7. Escuta + e-mail — um handler reage e dispara o side-effect (envia o e-mail).
  8. Projeção — um projector materializa a linha na tabela de leitura.
1

Controller

a porta HTTP — valida e delega

Recebe POST /catalog/products, valida o corpo contra o schema e chama o use case. Não toca repositório nem tem lógica.

Java · Spring BootCreateProductController.java
@RestController
@RequestMapping("/catalog/products")
public class CreateProductController {

  private final CreateProduct createProduct;

  public CreateProductController(CreateProduct createProduct) {
    this.createProduct = createProduct;
  }

  @PostMapping
  @ResponseStatus(HttpStatus.CREATED)
  public CreateProductOutput create(@Valid @RequestBody CreateProductInput body) {
    return createProduct.execute(body);
  }
}

// DTO de entrada (Bean Validation)
public record CreateProductInput(
    @NotBlank String name,
    @PositiveOrZero long priceCents) {}
API TypeScriptcontrollers/CreateProductController.ts
@injectable()
export class CreateProductController extends Controller<
  { body: typeof CreateProductInputSchema },
  typeof CreateProductOutputSchema
> {
  readonly path = '/products'
  readonly method = 'post'
  override middlewares = [AuthAccountMiddleware]

  readonly inputSchema = { body: CreateProductInputSchema }
  readonly outputSchema = CreateProductOutputSchema

  constructor(private readonly createProduct: CreateProduct) {
    super()
  }

  async handle(request: this['request']): Promise<this['output']> {
    return this.createProduct.execute(request.body)
  }
}

// schema de entrada — a MESMA fonte que valida o form no frontend
export const CreateProductInputSchema = z.object({
  name: z.string().min(1),
  priceCents: z.number().int().nonnegative(),
})
export const CreateProductOutputSchema = z.object({ productId: z.uuid() })
2

Use Case (no lugar do Service)

abre a transação e orquestra

No Java a lógica costuma cair num @Service gordo (um ProductService com create/update/delete). Aqui usamos um Use Case por intenção (CreateProduct, ActivateProduct…): ele só orquestra — abre a transação, pede para a entidade decidir, salva e persiste o evento. A regra de negócio fica na entidade (passo 3), não aqui. @Transactional vira withTransaction(tx, fn) — o tx é passado à mão.

E o Service? Existe aqui também — mas só para lógica que não cabe numa entidade (cálculo cross-entity, integração externa). Nunca como o lugar default da regra; essa mora na entidade.
Java · Spring BootCreateProduct.java
@Service
public class CreateProduct {

  private final ProductRepository products;

  public CreateProduct(ProductRepository products) {
    this.products = products;
  }

  @Transactional
  public CreateProductOutput execute(CreateProductInput in) {
    Product product = Product.create(in.name(), in.priceCents());
    products.save(product);     // Spring Data publica os domain events
    return new CreateProductOutput(product.getId());
  }
}
API TypeScriptusecases/CreateProduct.ts
@injectable()
export class CreateProduct extends Handler<
  typeof CreateProductInputSchema,
  typeof CreateProductOutputSchema
> {
  readonly inputSchema = CreateProductInputSchema
  readonly outputSchema = CreateProductOutputSchema

  constructor(private readonly products: ProductRepository) {
    super()
  }

  protected async handle(input, tx?): Promise<this['output']> {
    return this.withTransaction(tx, async (tx) => {
      const product = Product.create(input)
      await this.products.save(product, tx)
      await this.domainEventRepository.save(product.pullDomainEvents(), tx)
      return { productId: product.id.value }
    })
  }
}
3

Entidade

decide se é válido e levanta o evento

O coração do domínio. A regra de negócio mora aqui (não no use case): valida a invariante no create(), define o estado inicial e registra o domain event.

Java · Spring BootProduct.java
@Entity
@Table(name = "products")
public class Product extends AbstractAggregateRoot<Product> {

  @Id private String id;
  @Column(nullable = false) private String name;
  @Column(nullable = false) private long priceCents;
  @Enumerated(EnumType.STRING) private ProductStatus status;
  @Version private Long version;

  protected Product() {}                       // JPA exige no-arg

  public static Product create(String name, long priceCents) {
    if (priceCents < 0) throw new InvalidPriceException();   // invariante
    Product p = new Product();
    p.id = UUID.randomUUID().toString();
    p.name = name;
    p.priceCents = priceCents;
    p.status = ProductStatus.DRAFT;
    p.registerEvent(new ProductCreatedEvent(p.id, name));    // levanta evento
    return p;
  }

  public void activate() {
    if (status == ProductStatus.ARCHIVED) throw new ProductArchivedException();
    this.status = ProductStatus.ACTIVE;
  }

  public String getId() { return id; }
}

public enum ProductStatus { DRAFT, ACTIVE, ARCHIVED }
API TypeScriptentities/Product.ts
export const ProductSchema = z.object({
  id: z.instance(Id),
  name: z.string().min(1),                  // invariante: nome obrigatório
  priceCents: z.number().int().nonnegative(),   // invariante: preço nunca negativo
  status: z.enum(ProductStatus),
})

export class Product extends AggregateRoot<typeof ProductSchema> {
  static override schema = ProductSchema

  static create(data: { name: string; priceCents: number }): Product {
    // sem if manual: o construtor valida os props contra ProductSchema
    // (priceCents < 0 ou name vazio → erro de domínio levantado aqui)
    const product = new Product({
      id: Id.generate(),
      name: data.name,
      priceCents: data.priceCents,
      status: ProductStatus.DRAFT,
    })
    product.addDomainEvent(new ProductCreatedEvent({          // levanta evento
      entityId: product.id.value,
      payload: { productId: product.id.value, name: data.name },
    }))
    return product
  }

  activate(): void {
    if (this.props.status === ProductStatus.ARCHIVED)
      throw new BaseError<CatalogDomainErrors>('PRODUCT_ARCHIVED')
    this.props.status = ProductStatus.ACTIVE
  }
}

export enum ProductStatus { DRAFT = 'DRAFT', ACTIVE = 'ACTIVE', ARCHIVED = 'ARCHIVED' }

Repositório

persiste a entidade

A ponte entidade ↔ banco. A interface é o contrato; a implementação Drizzle é manual e recebe o tx (tx ?? this.db) para participar da mesma transação do use case.

Java · Spring BootProductRepository.java
// Spring Data gera a implementação automaticamente
public interface ProductRepository
    extends JpaRepository<Product, String> {

  Optional<Product> findByName(String name);
}
API TypeScriptrepositories/ProductRepository.ts
// Interface (contrato)
export abstract class ProductRepository extends Repository<Product> {
  abstract findByName(name: string, tx?: Transaction): Promise<Product | undefined>
}

// Implementação Drizzle
@injectable()
export class DrizzleProductRepository extends ProductRepository {
  constructor(private readonly db: DrizzleClient) { super() }

  async findById(id: string, tx?: Transaction) {
    const client = tx ?? this.db
    const [row] = await client.select().from(products)
      .where(eq(products.id, id)).limit(1)
    return row ? this.toDomain(row) : undefined
  }

  async save(product: Product, tx?: Transaction) {
    product.incrementVersion()
    await (tx ?? this.db).insert(products)
      .values(this.toPersistence(product))
      .onConflictDoUpdate({ target: products.id, set: this.toPersistence(product) })
    return product
  }

  private toDomain(row): Product { /* hidrata a entidade */ }
  private toPersistence(p: Product) { /* mapeia para colunas */ }
}

Evento

o fato, tipado

"Produto criado." Carrega um payload tipado e foi gravado no outbox junto com a entidade (passos 2 e 4). É o que será entregue aos assinantes.

Java · Spring BootProductCreatedEvent.java
public class ProductCreatedEvent {

  private final String productId;
  private final String name;

  public ProductCreatedEvent(String productId, String name) {
    this.productId = productId;
    this.name = name;
  }

  public String getProductId() { return productId; }
  public String getName() { return name; }
}
API TypeScriptevents/ProductCreated.ts

  productId: z.uuid(),
  name: z.string(),
})

export class ProductCreatedEvent extends BaseDomainEvent<
  typeof ProductCreatedSchema
> {
  static override readonly name = 'catalog.product.created' as const
  static readonly schema = ProductCreatedSchema
}

Disparo do evento

infra — acontece depois do commit

Você não escreve esse passo: é a infraestrutura. Depois que a transação commita, o evento é entregue a todos os assinantes (handlers e projectors). No Spring é o container; aqui é o OutboxDispatcher lendo a tabela e chamando o InternalMediator.

Escuta + envio de e-mail

um handler reage e faz o side-effect

Um handler assina o evento e dispara o efeito — aqui, mandar o e-mail. (É também daqui que sai um integration event para outro serviço, se necessário — nunca do use case.)

Java · Spring BootWelcomeEmailHandler.java
@Component
public class WelcomeEmailHandler {

  private final MailService mail;

  public WelcomeEmailHandler(MailService mail) {
    this.mail = mail;
  }

  @Async
  @TransactionalEventListener(phase = AFTER_COMMIT)
  public void on(ProductCreatedEvent event) {
    mail.sendProductCreated(event.getProductId(), event.getName());
  }
}
API TypeScripthandlers/internal.ts
@injectable()
export class WelcomeEmailHandler extends EventHandler<
  typeof ProductCreatedEvent
> {
  readonly event = ProductCreatedEvent

  constructor(private readonly mail: MailService) {
    super()
  }

  async handle(event): Promise<void> {
    await this.mail.sendProductCreated(
      event.payload.productId,
      event.payload.name,
    )
  }
}
8

Montagem da projeção

um projector materializa o read-model

Outro assinante do mesmo evento: o projector escreve a linha na tabela de leitura (product_list), otimizada para a listagem. Só escreve read-model — nenhuma regra de negócio.

Java · Spring BootProductListProjector.java
// tabela de leitura
@Entity @Table(name = "product_list")
public class ProductListRow {
  @Id private String id;
  private String name;
  private String status;
  // getters / setters
}

// projector: @EventListener que SÓ escreve read-model
@Component
public class ProductListProjector {

  private final ProductListRepository repo;

  public ProductListProjector(ProductListRepository repo) {
    this.repo = repo;
  }

  @TransactionalEventListener(phase = AFTER_COMMIT)
  public void onCreated(ProductCreatedEvent e) {
    ProductListRow row = new ProductListRow();
    row.setId(e.getProductId());
    row.setName(e.getName());
    row.setStatus("DRAFT");
    repo.save(row);
  }
}
API TypeScriptprojections/ProductListProjector.ts
// projection: free record (sem invariante), dona da criação
export class ProductListProjection {
  constructor(public props: ProductListProjectionProps) {}

  static create(event: ProductCreatedEvent): ProductListProjection {
    return new ProductListProjection({
      id: event.payload.productId,
      name: event.payload.name,
      status: ProductStatus.DRAFT,
    })
  }
}

// projector: handler do read-side, 1 por projection
@injectable()
export class ProductListProjector extends Projector<
  typeof ProductCreatedEvent
> {
  readonly events = ['catalog.product.created']

  constructor(private readonly repo: ProductListProjectionRepository) {
    super()
  }

  async handle(event, tx?): Promise<void> {
    switch (event.name) {
      case 'catalog.product.created':
        await this.repo.insertIfNew(ProductListProjection.create(event), tx)
        break
    }
  }
}
Resultado: os passos 1–4 rodaram numa transação (entidade + evento gravados juntos). Depois do commit, o mesmo evento alimentou dois assinantes em paralelo: o handler mandou o e-mail (passo 7) e o projector montou a linha de leitura (passo 8).
