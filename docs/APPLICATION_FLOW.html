template — How the whole thing flows

A polyglot e-commerce analytics platform built across TypeScript (Bun) and Go, fronted by React and Astro, backed by one Postgres. This document traces a request from the login screen, through connecting an external store, into the Go workers that ingest provider data in the background, and back out to the dashboards — naming the real files and mechanisms at each step.

DDD + Clean Architecture CQRS command/query split Event-driven via transactional outbox Contracts-first (TypeSpec → SDKs) Single Postgres, Drizzle migrations

00 Overview & topology

Five workspaces, two backends, three frontends, one database — glued by a generated SDK and a shared event log.

The platform's job is to connect a merchant's external systems (Shopify, Nuvemshop, Meta/Google/TikTok ads, payment checkouts) and turn the data into dashboards: sales, catalog cost, marketing spend, and a visitor funnel. The two backends divide labour by workload shape, not by feature:

01 Architecture principles

Every rule exists to keep bounded contexts independent so the system evolves without rewrites.

DDD — bounded contexts

Each business slice (sales, catalog, marketing, tenancy…) is a folder that owns its entities, use cases, controllers and DI wiring. Contexts never import each other's internals — they talk through events or each other's Repository.

Clean Architecture — dependency direction

HTTP controllers are thin (validate → call a use case → return). Use cases orchestrate domain entities + repositories inside a transaction. Entities hold the invariants. Nothing in the domain knows about HTTP or Drizzle.

CQRS — writes ≠ reads

Commands (use cases) load aggregates, enforce rules, and persist + emit events transactionally. Queries (the BFF) skip the domain and read straight from Drizzle into the exact DTO a screen needs.

Event-driven — the outbox

An aggregate change and its event are saved in one transaction to a shared.outbox table. A dispatcher later re-emits each event to in-process handlers, projectors, and (cross-service) the other runtime.

Why two languages share one database
The outbox/event log lives in Postgres, which both runtimes connect to. That shared, durable log — not a message broker — is the backbone that lets a Go worker's ingest trigger a TypeScript projection, and vice-versa, without either service calling the other's HTTP API directly.

1 Auth & login

Identity is delegated to better-auth; the domain reacts to it. Sessions carry the active store.

Login is owned by the auth context. auth/services/Authentication/BetterAuth.ts configures better-auth with a Drizzle adapter over the users, sessions, accounts and verificationTokens tables. It is mounted under /v1/authentication, uses UUIDv7 ids (so rows can carry domain events), and a customSession plugin adds an activeStoreId field — that is how a single login operates against a chosen store.

  1. The form submits. app/react/src/routes/sign-in/-components/SignInForm validates { email, password } with a Zod schema and calls auth.signIn.email(...) from the better-auth React client (app/react/src/lib/auth.ts, baseURL /v1/authentication). FE
  2. better-auth verifies & issues a session. Credentials are checked, a sessions row is created (with activeStoreId), and a session cookie is set on the browser. api-ts · auth
  3. The domain reacts. databaseHooks wired to IdentityAuthHooks fire on user create/update, letting the identity context build its own UserProfile / UserPreferences — keeping auth concerns and profile concerns separate. api-ts · identity
  4. Every later request is gated. AuthAccountMiddleware (auth/middlewares/AuthAccountMiddleware.ts) calls betterAuth.auth.api.getSession(), validates it, and attaches ctx.user + ctx.session to the request — or throws UNAUTHORIZED. api-ts · middleware
  5. Store access is enforced. RequireStoreMember checks the user owns a StoreMembership for the target store before a controller runs. api-ts · middleware
auth vs identity
auth is the HTTP/credential surface (sign-in, sign-up, sessions) driven by better-auth. identity is the domain side — UserProfile, UserPreferences, FCM tokens — that reacts to auth lifecycle hooks. Tokens, password resets and sessions are owned by better-auth and are never re-modelled as domain aggregates.

2 Tenancy & store context

A user belongs to one or more stores; nearly everything downstream is scoped by storeId.

The tenancy context owns Store, StoreMembership and StoreInvitation (tenancy/entities/). A Store carries a reporting currency and an IANA timezone — the timezone matters because analytics day-boundaries and notification timing depend on it (and it is auto-enriched from Shopify on integration, see §3).

  • The session's activeStoreId selects which store the dashboards read. Switching store is a session-level change, not a re-login.
  • Membership roles (owner / invitee) gate writes. Test fixtures mirror this with givenStoreWithOwner → givenUserWithAccount + givenStore + givenStoreMembership.
  • Cross-context reads inside the backend go through the other context's Repository — never the HTTP SDK (that would create a cycle).

3 Connecting an external platform

OAuth, credentials, or manual — all funnel into one activation chain that wakes the Go worker.

This is the hinge of the whole product: a merchant authorizes Shopify (or Meta/Google/TikTok/a checkout), the backend seals the secret, marks the integration active, and that fact crosses into Go to start the background sync. The shape of every platform lives in one typed registry, core/src/schemas/platform.ts (PLATFORM_REGISTRY / PlatformDescriptor), keyed by (type, platform) with a ConnectionMode of OAUTH, CREDENTIALS, or MANUAL.

3a · The OAuth flow

  1. Ask for an authorize URL. The app POSTs to AuthorizeIntegrationController (integration/controllers/AuthorizeIntegrationController.ts) with { type, platform, identifier? }. The AuthorizeIntegration use case resolves a per-platform AuthorizeUrlBuilder via a factory and returns { authorizeUrl, state } — state is a signed envelope (userId, storeId, platform). api-ts · integration
  2. Redirect to the provider. The browser sends the merchant to the provider's consent screen. FE → provider
  3. Provider calls back. IntegrationOAuthCallbackController (GET /integrations/oauth/callback/:platform) is public — the signed state is the credential. It verifies state, then calls ConnectIntegration with the provider's code. provider → api-ts
  4. Exchange + seal + persist. ConnectIntegration (integration/usecases/ConnectIntegration.ts) runs a per-platform OAuthCodeExchanger to get tokens, verifies them through a HandshakeService (e.g. ShopifyHandshaker), seals them with AesCredentialVault (core/src/services/CredentialVault/AesCredentialVault.ts, AES-256-GCM), and saves a StoreIntegration + IntegrationCredentialSecret row in one transaction. api-ts · integration
  5. Activation raises an event. Persisting emits the domain event IntegrationActivatedEvent. domain event
  6. Redirect back to the SPA. The callback returns a 302 with ?status=ok (never a JSON 4xx) so the browser lands cleanly. api-ts → FE

CREDENTIALS platforms skip steps 1–3 (the merchant types an API key, handled by a CredentialsExchanger); MANUAL platforms carry no secret at all. All three converge on the same StoreIntegration + IntegrationActivatedEvent.

4 Background sync (Go)

Two ways data arrives — pushed webhooks and pulled pipelines — both land in the same drain-and-upsert machine.

The Go service exists for one reason: ingest a lot of provider data, fast, and write it idempotently. Everything is wired with fx modules (internal/sync/module.go, internal/webhooks/module.go) and persisted with pgx. Each entity type owns a storage drain goroutine that boots at startup.

4a · Webhook ingest (push)

  1. Provider POSTs a webhook. POST /webhooks?platform&event&integrationId&storeId hits webhooks/controllers/webhook.go. The HMAC signature is verified (per-platform WebhookVerifierFactory), the body is deduped by IDFromSeed("webhook", platform, sha256(body)), a WebhookReceivedEvent is written to the outbox, and the endpoint returns 202 immediately. api-go · webhooks
  2. The receiver maps the body. Off the outbox, webhook_received_handler.go resolves mappers.Factory.Get(platform, event) (webhooks/mappers/factory.go) and turns the raw payload into one or more normalized sync.ExternalXUpdatedEvents (e.g. ExternalOrderUpdatedEvent carrying an OrderInput). api-go · webhooks
  3. The entity handler rebuilds the aggregate. order_updated_handler.go calls entities.NewOrderFromProviderPayload(input) (which validates + computes a deterministic Id.fromSeed primary key) and enqueues it on the storage's buffered InputChannel() — decoupling HTTP intake from the DB write. api-go · sync
  4. The drain batches & upserts atomically. storage/order/order_pg.go's Start() loop accumulates via Accumulator[*Order] (core/types/accumulator.go, batch 1000 / flush 1s) and, on flush, runs one UnitOfWork transaction: bulk INSERT … ON CONFLICT (id) DO UPDATE for every row and writes the wire integration event (e.g. OrderUpdatedEvent) to the outbox — all-or-nothing. api-go · sync
The drain pattern (memorize this — it repeats for every entity)
ExternalXUpdatedEvent → handler rebuilds aggregate → storage.InputChannel() → Accumulator → bulk UPSERT + outbox event in one tx. Orders, products, variants, transactions and pixel events all follow it. The buffered channel is what lets the HTTP layer answer 202 in milliseconds while the heavy write happens behind it.

4b · Sync pipelines (pull)

For data providers don't push, pipelines fetch it. Each implements the Pipeline interface (sync/services/pipelines/pipeline.go): Platform(), Pipeline(), and Run(ctx, RunInput, publisher). RunInput carries StoreID, StoreIntegrationID, the unsealed Credentials, a WindowDays for backfills, a JobID, and a Mediator. A pipeline fetches → normalizes → publishes ExternalXUpdatedEvents — it never writes the DB itself; the same handler+drain from §4a does the persistence. A SyncJob tracks state (running/completed/failed) and is run on demand (e.g. POST /sync/jobs) — the TS side can kick one via the SDK Client.go.sync(...).

5 Event architecture

Two kinds of events, one durable log, a dispatcher that fans out — the seam that keeps contexts and languages decoupled.

Domain event

A fact inside one context. Raised by an entity, handled in-process by that context's handlers/projectors via the InternalMediator. Never crosses a service. e.g. IntegrationActivatedEvent, WebhookReceivedEvent.

Integration (wire) event

A fact that crosses contexts or services. Its schema is defined once in contracts/wire/events/*.tsp (TypeSpec) and code-generated into Go + TS bindings. Published only by handlers. e.g. OrderUpdatedEvent, PixelEventRecordedEvent.

The transactional outbox

The core trick: a write and its events are committed together. The use case (or Go storage drain) saves the aggregate row and an event row into shared.outbox in the same transaction. There is no window where the data changed but the event was lost. An OutboxDispatcher then runs independently on each side (go: core/services/outbox/outbox_dispatcher.go; ts: DrizzleOutboxDispatcher), polling the table in batches with adaptive backoff, grouping by owner_id, and re-emitting each event through the mediator so subscribers react as if it were in-memory.

How Go and TS hear each other
Both runtimes connect to the same Postgres, so the durable shared.outbox is the cross-service backbone — a Go drain's OrderUpdatedEvent becomes visible to TS handlers, and a TS handler's integration.activated reaches the Go worker. In production the external/integration channel is additionally fronted by Redis (RedisExternalMediator + BullMQ) for low-latency fan-out; in tests it is an in-memory SpyMediator. The outbox is always the source of truth.

6 Canonical aggregates vs read-models

Provider data is owned (written) by Go; the dashboards read TypeScript-side projections derived from the wire event.

This is the most important consequence of the split. For provider-synced entities like Order, Product and Variant, the write authority is the Go sync context — its aggregates are the single source of truth, upserted idempotently by deterministic Id.fromSeed(platform, externalId, …) keys. The wire event (OrderUpdatedEvent) is the contract. TypeScript does not re-derive these from a shared schema; it subscribes to the event and maintains its own read-model, plus any local concerns it owns outright.

A read shape that is just a join becomes a QueryService; only genuine denormalization or cross-context aggregation becomes a projection.

No event sourcing for domain entities
Aggregates use plain imperative methods (activate(), cancel()). Events are for logs and for triggering downstream handlers — not for rebuilding entity state. Event sourcing only ever applies to projections, via the canonical find → applyEvent → save flow.

7 Pixel tracking (the funnel)

Browser-origin, unsigned, high-volume — with a Redis throttle and a 24h backfill to keep the funnel honest.

The storefront pixel posts visitor events (page view → product view → add-to-cart → checkout → completed). Unlike provider webhooks these are unsigned and browser-origin, so they take a dedicated branch and extra safety.

  1. Unsigned intake. The same /webhooks endpoint takes a type=PIXEL_EVENT branch (webhooks/controllers/webhook.go): no HMAC, the client asserts only platform + storeIntegrationId, and the storeId is resolved server-side — never trusted from the client. api-go
  2. Resolve the store (cached). A saleschannel.Resolver (sync/services/saleschannel/resolver.go) maps the immutable storeIntegrationId → (storeId, externalId) from integration.store_integrations, cached in memory. api-go
  3. Throttle per visitor. A Redis SETNX throttle (sync/services/pixelthrottle/throttle.go) drops duplicate noise per (eventType, visitorKey, storeIntegrationId) with per-type TTLs (page view 60s, product view 5m, cart events 30m). CHECKOUT_COMPLETED is never throttled. api-go · Redis
  4. Backfill missing stages. Pixels only emit the stage that just happened, so a visitor who lands straight on checkout would undercount the top of the funnel. The handler reads the visitor's last-24h stages (DistinctStagesForVisitor) and SynthesizeMissingStages fabricates the earlier steps so the funnel adds up. api-go · pixelbackfill
  5. Drain + publish. Real + synthetic events go through the standard drain (§4a) into tracking.pixel_events, and a PixelEventRecordedEvent is published. api-go → outbox
  6. Read + link. TS tracking projects the funnel for the dashboard (GetPixelFunnel); TS sales reacts to CHECKOUT_COMPLETED to link the visitor's Cart → Order. api-ts

8 Marketing pipelines

A hierarchy (BM → ad account → campaign → ad set → ad + spend) synced concurrently, with a polymorphic access link on the TS side.

Each ad platform (Meta, Google Ads, TikTok) ships four pipelines: BUSINESS_ACCOUNTS, AD_ACCOUNTS, CAMPAIGNS (one pipeline walks the campaign→ad-set→ad tree), and MARKETING_METRICS. The hierarchy is written as six Go canonical aggregates (business_account, ad_account, campaign, ad_set, ad, ad_spend) via the §4 drain pattern.

Concurrency runtime

Metrics backfills span many days, so sync/services/runtime/ provides shared primitives: DayWorkerPool (workers consume days from a buffered channel, first-error-wins), ProgressPublisher (atomic counter + 5%-step gate that emits a progress wire event), and a RateLimiter port (header-adaptive for Meta).

The TS access link

When a pipeline discovers a business account or ad account, Go publishes MarketingBusinessAccountDiscoveredEvent / MarketingAdAccountDiscoveredEvent. Two TS handlers (marketing/handlers/external.ts) upsert a polymorphic row in marketing.store_integration_marketing_access — bridging a StoreIntegration to the assets it can see, with active / validFrom / validTo per row. The composite key (storeIntegrationId, accessType, platform, externalId) makes re-discovery an idempotent UPSERT, never a duplicate.

Manual vs automatic spend
Automatic ad-spend lives in Go's sync.ad_spend. The TypeScript side keeps only the manual spend the merchant types in, as the AdSpendManual aggregate — the name makes the scope unambiguous. Campaign reads route to Go via the SDK; the only TS-local campaign concept is CampaignProductBinding (a manual user mapping keyed by the provider's campaignExternalId).

9 Queries (BFF) & the SDK

Reads skip the domain and shape Drizzle straight into the screen's DTO. The contract is a generated, typed SDK.

A read is a Query Use Case: it does not load aggregates, it queries Drizzle and returns exactly what one view needs. Take the funnel dashboard:

  1. The component calls a hook. A funnel section calls the generated hook (useGetPixelFunnel(...)) — a React Query wrapper with a stable query key. FE
  2. The hook hits a GET controller. GetPixelFunnelController validates query params { storeIds, from, to } (behind AuthAccountMiddleware) and calls the use case. api-ts · tracking
  3. The use case reads Drizzle. GetPixelFunnel (tracking/usecases/GetPixelFunnel.ts) aggregates tracking.pixel_events into stages — counts, unique sessions, drop-off % — and returns a typed OutputSchema. api-ts
  4. The shape round-trips type-safe. Because the controller's Zod schemas drive the OpenAPI spec, the hook's response type already matches the use case's output. contract

10 Frontend composition

Routes are thin shells; components own their own data; forms reuse the backend's Zod.

  • Route — a URL shell (app/react/src/routes/(app)/…). Declares the path/search-param contract, breadcrumb and layout, and decides which components appear. It does not fetch data to pass down.
  • Component / Section — each owns its own data: reads search params via the route API, reads client state from a Zustand store, and fires its own SDK query/mutation hooks. While loading it renders a skeleton inline; static UI stays visible. Container sections use the Section name suffix as convention.
  • Leaf — pure presentational pieces rendered in a .map() (cards, rows, badges) receive their item by prop.
  • Form — TanStack Form validated by the same Zod schema the controller uses (from the SDK) — zero manual sync between client and server validation.
  • Primitive — design-system atoms (Button, Dialog) over Base UI + CVA, sharing tokens from packages/app/styles.
